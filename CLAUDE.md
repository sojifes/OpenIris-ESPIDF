# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OpenIris-ESPIDF is the ESP-IDF firmware (C/C++) for OpenIris eye/face trackers, plus Python tools for board configuration and device setup. It targets multiple ESP32 / ESP32-S3 boards under `boards/`.

ESP-IDF version: **v5.4.2** (see `.github/workflows/build-and-release.yml`).

## Common commands

All Python tooling is run via `uv`. The firmware is built with `idf.py` from an ESP-IDF environment (`. $IDF_PATH/export.sh` or the VS Code "ESP-IDF Terminal").

### Board selection (must be done before build)

`sdkconfig` is generated by overlaying `boards/sdkconfig.base_defaults` with the chosen board file under `boards/`. Always use the helper script — do NOT hand-edit `sdkconfig` for board switches.

```bash
uv run ./tools/switchBoardType.py --list
uv run ./tools/switchBoardType.py --board <board_key> --diff
```

The board key is the path under `boards/` with `/` replaced by `_`, with duplicate trailing segments collapsed (e.g. `boards/project_babble/project_babble` → `project_babble`).

### Firmware build / flash

```bash
idf.py set-target esp32s3        # or esp32 — see workflow matrix for the right target per board
idf.py build
idf.py -p <PORT> flash monitor
```

The CI build matrix in `.github/workflows/build-and-release.yml` is the source of truth for which `target` each board needs.

### Device setup CLI (over USB serial / CDC)

```bash
uv run ./tools/setup_openiris.py --port <COMxx | /dev/ttyXXX>
```

Close any open serial monitor first — the port must be free.

### Hardware-in-the-loop tests

Tests live in `tests/` and require a real board plugged in. Copy `tests/.env.example` → `tests/.env` and fill in `WIFI_SSID`, `WIFI_BSSID`, `WIFI_PASS`, plus the timeout values (`SWITCH_MODE_REBOOT_TIME`, `WIFI_CONNECTION_TIMEOUT`, `INVALID_WIFI_CONNECTION_TIMEOUT`).

```bash
# all tests
uv run pytest --board=<board_name> --connection=COM<n>

# single test
uv run pytest --board=<board_name> --connection=COM<n> -k <name_substring>

# rerun last failures
uv run pytest --board=<board_name> --connection=COM<n> --lf
```

`board_name` here matches a key in `tests/conftest.py::board_capabilities` (not always identical to the `switchBoardType.py` key — e.g. `facefocusvr_eye_L`). Tests are auto-skipped on boards lacking the required capability via `@pytest.mark.has_capability(...)` / `lacks_capability(...)`.

**Warning:** The test session ends by sending `reset_config { "section": "all" }` and restarting the device. Any manual settings on the board will be wiped — there is no opt-out.

### Code style

`.clang-format` is Google-based with Allman braces, 4-space indent, 160-col limit. Run clang-format before committing C/C++ changes.

## Architecture

### Boot flow (`main/openiris_main.cpp`)

`app_main()` wires up everything as globals at file scope, then:

1. Initializes NVS, loads `ProjectConfig` from preferences, sets up LED + camera + serial manager.
2. Starts long-lived FreeRTOS tasks: `HandleStateManagerTask`, `HandleLEDDisplayTask`, `HandleSerialManagerTask` (and `HandleCDCSerialManagerTask` once UVC takes over).
3. Branches on `deviceConfig->getDeviceMode()`:
   - **UVC** → `startWiredMode(true)`: shuts down `SerialManager`, hands USB over to TinyUSB, starts `UVCStreamManager` + CDC command channel.
   - **WIFI** → `startWiFiMode()`: starts `WiFiManager`, `MDNSManager`, `RestAPI`, `StreamServer` (HTTP MJPEG on :80, REST on :81).
   - **SETUP** → starts WiFi services AND a one-shot `esp_timer` (`startSetupMode`) that fires after `CONFIG_GENERAL_STARTUP_DELAY` seconds. If no command arrived during the delay (`getStartupCommandReceived()` / `getStartupPaused()`), it auto-launches the configured streaming mode.

The serial/CDC handover is delicate: `startWiredMode` deletes the serial manager FreeRTOS task and uninstalls the driver, waits 200 ms for the host to see the COM port disappear, then sets `setUsbHandoverDone(true)` before initializing TinyUSB. Don't reorder these steps.

### Command framework (`components/CommandManager`)

All control flows — REST, classic serial, and CDC — funnel through one place:

- `CommandManager::executeFromJson(...)` parses a JSON envelope `{"commands":[{"command":"name","data":{...}}, ...]}` and dispatches each entry.
- Command implementations live in `components/CommandManager/CommandManager/commands/*.cpp` grouped by domain (camera, config, device, mdns, scan, simple, wifi).
- Commands resolve their dependencies (CameraManager, WiFiManager, ProjectConfig, LEDManager, MonitoringManager) via `DependencyRegistry`, which is populated in `app_main` BEFORE any task starts. To add a new dependency: add an enum value in `DependencyType`, register it in `app_main`, and call `registry->resolve<T>(...)` from the command.
- WiFi-related commands and the `WiFiManager` service are only registered when `CONFIG_GENERAL_ENABLE_WIRELESS` is defined — wired-only builds intentionally don't expose WiFi commands.
- `CommandType` enum in `CommandManager.hpp` is the canonical list — when adding a command, update the enum, the dispatch in `createCommand`, and the relevant `commands/*` file.

The same JSON envelope is accepted over HTTP (`RestAPI`), classic UART (`SerialManager`), and TinyUSB CDC (`HandleCDCSerialManagerTask`). Responses are JSON and flushed immediately.

### State + LED indication (`components/StateManager`, `components/LEDManager`)

Subsystems push `SystemEvent { source, value }` (variant of WiFi/MDNS/Camera/Stream state enums) onto `eventQueue`. `HandleStateManagerTask` consumes events and pushes `LEDStates_e` codes onto `ledStateQueue`, which `HandleLEDDisplayTask` renders as blink patterns. New subsystems should publish via the `eventQueue` rather than touching the LED queue directly. `SendStreamEvent` in `StateManager.hpp` is the helper for stream-state pushes.

LED behavior splits between `LED_DEBUG_*` (status LED) and `LED_EXTERNAL_*` (IR LED). When `LED_EXTERNAL_AS_DEBUG` is set, error patterns mirror to the IR LED at 0%/50% duty — non-error patterns are deliberately not mirrored.

### Configuration sources

Three layered sources, in order of precedence at runtime:

1. **Kconfig (compile-time)** — `Kconfig.projbuild` files in `main/` and components define `CONFIG_*` symbols. Defaults baked into firmware.
2. **Board overlay (build-time)** — `boards/<board>/...` files override defaults via `switchBoardType.py`. Always overlay on top of `boards/sdkconfig.base_defaults`.
3. **`ProjectConfig` (runtime)** — persisted to NVS via `Preferences`. Holds user-set device name, WiFi credentials, mode, LED PWM, etc. Runtime values supersede the compile-time `CONFIG_GENERAL_ADVERTISED_NAME`.

When adding a new board: create the file under `boards/<family>/<variant>` with only the deltas vs `sdkconfig.base_defaults`, then add it to the CI matrix in `.github/workflows/build-and-release.yml` and (if HIL-tested) `tests/conftest.py::board_capabilities`.

### Optional features behind Kconfig

Several modules are guarded by Kconfig flags and add their own globals/tasks only when enabled. Mirror these guards in any new code that touches them:

- `CONFIG_GENERAL_INCLUDE_UVC_MODE` — UVC streaming + composite USB. Without it, UVC mode falls back to WiFi.
- `CONFIG_GENERAL_ENABLE_WIRELESS` — WiFi/mDNS/REST stack. Wired-only builds skip these entirely.
- `CONFIG_MONITORING_LED_CURRENT` / `CONFIG_MONITORING_BATTERY_ENABLE` — `MonitoringManager` and the `get_led_current` / `get_battery_status` commands.
- `CONFIG_LED_DEBUG_ENABLE` / `CONFIG_LED_EXTERNAL_*` — debug + IR LED GPIO control.
